## 触发

问完俄罗斯农夫的复杂度（[[halve-is-not-log]]）之后追问：
「进制对于做乘法很关键？」，然后自己提了个框架——
**base 只是决定乘法表多大、什么东西可以 O(1) 查，本质是个空间时间的 trade？**

## 卡点 / 误解

**这个框架方向是对的**，但我默认它是笔**划算**的买卖。量化之后完全不是。

设输入 n 个 bit，每个数字占 w 个 bit（base b = 2^w）：

```
数字个数     = n / w
数字乘法次数 = (n/w)²  ~  n²/w²      ← 时间，按 w 平方衰减
乘法表条目数 = b² = 4^w              ← 空间，按 w 指数增长
```

**时间只是平方级地变好，空间是指数级地变坏。** 想把时间砍一半，w 要 ×√2，
空间就从 4^w 变成 4^(1.41w)。

| base | w | 表条目 | 相对时间 |
|---|---|---|---|
| 2 | 1 | 4 | 1 |
| 10 | ~3.3 | 100 | 1/11 |
| 256 | 8 | 65536 | 1/64 |
| 2⁶⁴ | 64 | 3.4×10³⁸（比宇宙原子数还多） | 1/4096 |

所以对**固定的 base**，这永远是纯常数因子，`Θ(n²)` 不动。

**另一条纠正**（agent 上一轮给的说法有误导）：说「GMP 用 base 2⁶⁴」时
很容易脑补成一张巨表——**没有人存 2¹²⁸ 条目的乘法表**。CPU 做 64×64
用的是**电路**不是内存：

```
查表视角:  空间 = 4^w      指数      → w=64 物理上不可能
电路视角:  面积 = O(w²) 门  多项式    → w=64 约 4096 个门，小菜一碟
```

Wallace tree 乘法器就是把竖式布线成硬件。**那个 O(1) 原语是用电路面积买的，
不是用内存买的**，而电路的兑换率（w²）比查表（4^w）好得离谱。这就是为什么
现实中 w 能推到 64，而纯查表方案卡在 w≈16。

顺带：「O(1) 查询」本身也是模型假设——4^w 条目的表光寻址就要 2w 个 bit。

## 关键 insight

**别把 w 当常数。** 让它随 n 长，这个 trade 真能越过渐近边界：

取 `w = ½·log₂ n`：

```
表条目   = 4^w = n                ← 多项式空间，完全可行
建表代价 = n · O(w²) = O(n log²n) ← 比乘法本身便宜
乘法时间 = (n/w)² = Θ(n²/log²n)   ← 真的赢了渐近
```

「预计算一张 log 大小的表，把 log 个基本操作打包成一次查表」这类技巧统称
**Four Russians 方法**（布尔矩阵乘法等地方也用）。

但注意它**只赚到 log 因子**，跟 Karatsuba 的 `n^1.585` 完全不是一个量级——
这正是 [[change-model-vs-change-algorithm]] 里「改模型」那条路的天花板。
